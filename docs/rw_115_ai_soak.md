## 单位死亡后生产单位的编号续接

原版 `units/y.java:a(ab, boolean)` 会在普通移动单位陆地死亡时创建两个继承 `GameObject` 的死亡特效发射器；若焦痕的邻域上限允许，还会再创建一个继承 `GameObject` 的焦痕。此前 Godot 的死亡表现没有计入这几个全局编号，因此坦克被摧毁后，工厂下一辆坦克会拿到偏小的本地 ID，服务器仍能让复刻版移动它，但原版收到该 ID 时找不到对应坦克

现在 `BattleMap` 在销毁回调中按原版顺序推进这三个对象编号，并用路径网格的液体标记与原版 5 / 25 单位邻域阈值决定是否分配焦痕 ID。`rw_battle_combat_test.gd` 覆盖首次陆地死亡、相邻死亡和液体地形。此前五分钟 AI 轨迹未出现单位死亡，因此当时尚无在线第二辆坦克验证结果

带逐帧弹体记录的 `rw115-ai-soak-20261006-233253` 运行 120 秒，完成 25 个已验证校验点，原版没有 desync 或 resync。单位首个字段差异在第 2212 帧（建造者推力），首个网络校验差异在第 2408 帧。对象编号到 343 仍对应；编号 344 首先分叉：复刻炮兵 `c_artillery` 在第 5958 帧发射炮弹，原版该编号直到第 5976 帧才分给新单位；原版炮兵到第 6014 帧才发出编号 345 的炮弹。样本中一次陆地死亡两边都创建两个发射器和焦痕，但编号已因更早分叉相差 1。此局仍未重现“工厂第一辆坦克死亡后第二辆移动命令不被原版看到”的手动场景，不能据此判定其具体触发点

`BattleMap` 现记录移动命令发送和服务器回显时的单位编号、本地单位类型与位置，也记录单位生产编号及死亡特效消耗的编号。手动复现后可用这些行确认第二辆坦克的 ID 是否已在生产前偏移，或服务端回显时本地是否把该 ID 绑定到错误单位
